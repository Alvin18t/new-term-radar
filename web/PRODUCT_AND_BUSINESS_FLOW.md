# 产品架构与业务流程

## 1. 产品目的

这个产品的核心结果不是“每天发现更多词”，而是让个人开发者更快找到值得验证的市场，并用真实用户和付费结果校准下一轮选择。

建站、开发、部署和收款发生在产品之外。产品负责记录机会判断、个人决定、站点/页面覆盖、渠道动作和最终结果。

## 2. 六段闭环

| 阶段 | 输入 | 核心处理 | 输出 | 责任方式 |
|---|---|---|---|---|
| 持续发现 | X、Hugging Face、GitHub、Sitemap、新站、Reddit、收入、新卖家、GSC | 去重、聚类、名称判断、时间线 | 候选词与原始证据 | 自动 |
| 证据评估 | 搜索量、Trends、SERP、弱结果、KD、商业信号 | 需求/时机/竞争/商业/个人匹配评分 | 可以做、值得做、建议做、高净值 | 自动 + 深度模型 |
| 个人决策 | 偏好、时间、预算、技能与当前目标 | 人工选择和原因记录 | 待决定、计划做、在做、暂缓、不做 | 人工 |
| 站外建站 | 机会卡、首个页面、验证指标 | 外部设计、开发、部署和收款 | URL 与上线状态 | 系统外 |
| 统一运营 | 站点、页面、关键词、渠道资产 | 覆盖管理、外链/社媒行动、进度更新 | 下一动作与执行记录 | 人机协作 |
| 结果复盘 | 14 天趋势、排名、点击、注册、使用、付费 | 对比原判断、归因、记录失败原因 | 命中率、领先天数、规则调整 | 自动 + 人工 |

## 3. 两类状态必须分开

### 系统判断

`可以做`、`值得做`、`建议做`、`高净值` 是可并存的标签。它们来自不同证据维度，不应压缩成一个状态。

### 用户决定

`待决定 → 计划做 → 在做 → 已完成/暂缓/不做`。用户改变决定不会改写历史系统判断。

### 覆盖状态

关键词到页面使用 `未覆盖 / 已规划 / 已上线 / 需更新`；站点使用 `规划中 / 在线 / 暂停 / 下线 / 放弃`。覆盖也不应和用户决定混为一谈。

## 4. 推荐分层

机会分由六类证据组成，并保留可解释的子分：

1. 需求：搜索规模、增速、重复求助。
2. 时机：首次出现、扩散速度、跨来源共振。
3. 竞争：首页弱结果、页面类型、KD 与供应增量。
4. 商业：收入、新卖家、广告、明确付费场景。
5. 可执行：个人技能、预算、可在 1–2 周形成首个成功时刻。
6. 个人匹配：当前方向与全局探索策略。

系统要展示“为什么现在”“为什么适合你”“最小验证动作”和“什么结果会推翻判断”。

## 5. 多源关键词校验

热度只负责把词送入评估队列，不直接产生“建议做”。每个来源保留原值、时间、地域、查询路径和可信状态，禁止把不同口径简单平均成一个分数。

| 证据层 | 当前仓库真实来源 | 作用 | 行动门槛 |
|---|---|---|---|
| 发现 | X、Hugging Face、GitHub、Sitemap、新站、Reddit | 找到候选词和首次出现时间 | 只进入候选池 |
| 需求 | Google Trends；Google Ads 搜索量 | 验证增长是否持续、规模是否足够 | 新词可暂缺完整量级，但趋势与重复需求不能同时缺失 |
| 竞争 | Google SERP、KD、首页弱结果、真实结果 URL | 判断页面类型、强弱结果、已上线相关站点和候选竞品地址 | 必须完成，缺失时不能标记“建议做” |
| 站点强度 | GoAnyAPI DR；traffic 访问量代理 | 评估首页域名与候选站点强度 | 允许部分缺失，但必须降低置信度 |
| 供给与广告 | Intitle 新增页面、Ads Transparency 广告主 | 判断供给增速和付费获客证据 | 与商业证据至少有一组可用 |
| 商业 | TrustMRR、公开收款链接与卖家网络 | 验证是否有人正在收钱 | “高净值”必须有可追溯商业证据 |
| 个人匹配 | 时间、预算、技能、正反馈速度 | 判断是否适合当前阶段执行 | 必须通过，且不改写原始市场证据 |

当前代码对供应商的真实边界：

- DataForSEO 承担 Trends、Google Ads 搜索量、SERP、KD、WHOIS 和 Backlinks 等监控查询：有 `DATAFORSEO_LOGIN` 和 `DATAFORSEO_PASSWORD` 时直连，否则走 AIsa 备用路由。AIsa 另外承担社媒发现与模型提取。
- 同一次 SERP 查询保存最多 5 个可访问的非论坛、非视频结果 URL，不增加请求次数；工具页标记为“候选竞品”，其他结果保留为“相关页面”。与本周 WHOIS 新站结果命中时，再附注册与首次收录时间。
- GoAnyAPI 承担相关查询、国家日趋势、DR、Intitle、广告主和 traffic 访问量代理。
- 已增加 Ahrefs Keywords Explorer v3 直连适配器，读取搜索量、KD、CPC、点击、流量潜力、父主题、意图和 SERP 特征。
- 已增加 Semrush Keyword Metrics v4 直连适配器，读取搜索量、KD、CPC、付费竞争密度、意图、趋势和 SERP 特征。
- 已增加 Similarweb Batch API 非阻塞适配器：对最终候选词的首页域名提交访问与参与度报告，后续监控轮次查询状态、下载并缓存结果。
- 当前机器未配置三家付费 API 凭证。产品显示“适配器已就绪/待凭证”，只有收到真实响应后才显示“已校验”。

未来适配器按来源独立保存，不覆盖现有值：Ahrefs 用于流量潜力、反链与父主题；Semrush 用于搜索意图、CPC、付费密度和关键词差距；Similarweb 用于入围站点的地域、渠道结构和访问参与度。来源冲突时进入人工复核，不由模型自行抹平。

成本采用漏斗控制：第一层批量跑 Trends 与 Ads；第二层只给候选词跑 SERP、KD、DR、Intitle 和广告；第三层只给最终入围词按需调用 Ahrefs、Semrush 或 Similarweb。这样不会为了检查每个热词而同时消耗所有付费 API。

## 6. 模型与调度策略

- 采集任务不使用大模型时不调用模型。
- 高频分类、去重和摘要使用低延迟模型。
- 只有多源证据齐全、排名接近或用户主动要求时，才触发最强模型做深度机会判断。
- 频率按来源独立配置：新热词可 2–15 分钟，Sitemap/GSC 可 1–6 小时，稳定老词每日，收入与新卖家每周，复盘按到期任务运行。
- 设置每日成本上限、并发、退避、缓存和失败重试；“页面刷新”与“后台抓取”分开。

## 8. 生产数据层需要补充

在现有 `leads` 表之外增加：

- `keyword_opportunities`：标准词、类型、评分和系统标签。
- `evidence_events`：来源、URL、抓取时间、原文摘要和可信度。
- `user_decisions`：决定、原因、时间和历史版本。
- `market_sites`：关键词、域名、实际页面 URL、SERP 排名、页面类型、候选竞品标记和首次检测时间。
- `sites`、`site_pages`、`keyword_page_links`：站点、页面和覆盖关系。
- `channels`、`keyword_channel_plans`、`distribution_events`：渠道规则、内容方向和发布结果。
- `outcome_snapshots`：排名、点击、注册、激活、付费与留存。
- `preference_profiles`：全局/方向模式、预算、时间和目标。
- `source_schedules`、`job_runs`：调度、成本、状态和失败原因。
- `provider_observations`：供应商、指标名、原始值、单位、地域、查询时间、代理/直连状态和失败原因。
- `verification_runs`：每次多源校验的覆盖率、冲突项、门槛结果、模型版本与判断版本。

## 9. 业务指标

北极星指标：每 30 天由系统发现、经用户选择并最终产生真实付费用户的机会数。

过程指标按因果顺序查看：

1. 证据完整率与推荐可解释率。
2. 推荐到人工决定的时间。
3. 决定到站点/页面上线的时间。
4. 上线到首个真实用户和首个付费的时间。
5. 趋势、首页、用户、付费四级命中率。
6. 不做/暂缓决策的正确率与机会成本。
